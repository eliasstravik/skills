# landingpage-readme — intent

Date: 2026-07-26. Source plan:
`~/.consultant/landingpage-readme-skill/plan.md`.

## Real job

`landingpage-readme` is a user-invoked create-or-rewrite workflow for a GitHub
repository's full landing surface: README, About description, topics, and a
manual social-preview specification. It treats a missing README as the
emptiest audit, inspects repository evidence before asking only genuine gaps,
and aims the page at a developer's smallest useful install or first-run action.

The internal design model is never published. Reader-facing prose, headings,
metadata, topics, and HTML comments must look like an excellent ordinary
developer README and contain no behavior-design framework vocabulary.

## Output contract

- Inspect manifests, code, docs, README content, license, and assets first.
- Resolve actor, useful behavior, behavior chain, smallest first-run block,
  arrival moment, friction facts, evidence, adoption commitment, and visual
  availability.
- Ask one unresolved consequential question at a time.
- Invoke `/copywriting` for every audience-facing tagline, intro, heading, and
  call to action.
- Stop with an install instruction if `/copywriting` is unavailable.
- Present the complete README, metadata, exact `gh` commands, and social handoff
  before mutation.
- After approval, write the README and apply or emit approved GitHub metadata
  commands according to the environment.
- Reuse suitable repository visuals; otherwise leave a marked placeholder with
  an actionable hidden production specification.
- Omit unverified proof from approved output.

## Evaluation seam

The highest seam is a fresh one-shot executor running the full interactive
contract against a copied synthetic repository. Ground-truth keys outside the
fixtures distinguish inspectable facts, genuine gaps, and acceptable-to-ask
borderline facts. Scripted replies cover both landingpage-readme and composed
copywriting gates. Pure baselines forbid all installed skills. Every normal
case produces a transcript, approved README, metadata artifacts, and social
specification without executing `gh`.

## Model policy

- GPT-5.6 Sol for executor arms and judgment-heavy implementation.
- GPT-5.6 Terra for mechanical grading and contamination checks.
- GPT-5.6 Luna for repeated trigger decisions, comparison, and analysis.
- No Claude Code, Claude model, Fable, `claude`, `claude -p`, or transitive
  prohibited helper at build time.
- Final dogfood on Elias's real runtime is the sole approved exception.

## Gates

1. Elias approves all eval prompts, scripted replies, trigger queries,
   preflight prompt, and masked-dependency fiction.
2. The ungraded composed-environment preflight passes before graded runs or live
   copywriting mutation.
3. Pure baselines preserve at least one recurring failure.
4. A one-Recipe bare core is tested before any Details.
5. Only failed bare-core assertions earn Details or a one-level reference.
6. Elias reviews generated viewers.
7. Optimizer descriptions are applied verbatim and form is manually checked.
8. Elias approves live `gh` application and chooses the dogfood repository.
9. A complete standards/spec review passes before Elias's done-gate.
