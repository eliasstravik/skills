# Landingpage README
## Recipe
1. Inspect the manifest, implementation, docs, current README, license, and visual assets before asking questions.
2. Derive the actor, useful behavior, first-success chain, requirements, commitments, proof, and visual availability from repository evidence.
3. Ask one unresolved consequential question at a time.
4. Read [the exact landing-page README structure](references/exact-structure.md) before drafting variants.
5. Invoke `/copywriting` with the evidence, approved replies, and exact formulas for every audience-facing tagline, introduction, heading, and call to action.
6. Generate ten complete copy variants around distinct truthful angles unless the user specifies another count.
7. Present the variants in one paginated preview.
8. Propagate each user correction across every variant until one is approved.
9. Assemble the selected GFM README around the smallest truthful path to first success and its immediate result.
10. Add every evidence-supported section in the reference order.
11. Reuse suitable visuals with accessible GitHub-safe markup.
12. Specify each missing visual in an HTML comment as input → behavior → result production guidance.
13. Make `docs/getting-started.md` the primary self-serve CTA destination.
14. Prepare the About description, focused topics, manual social-preview specification, and exact `gh` metadata commands.
15. Present the complete landing surface and proposed commands before target-repository or GitHub mutation.
16. Await explicit approval.
17. Write the approved README, getting-started guide, assets, and social-preview specification.
18. Execute the explicitly approved metadata disposition: live `gh` mutation or saved exact commands.

## Details

- In normal flow, do not read or invoke `/copywriting` until repository inspection and gap resolution are complete; pass it the inspected evidence and approved replies.
- After `skill_not_found: copywriting`, respond only with `npx skills add eliasstravik/skills --skill copywriting -g`; draft nothing and change nothing.
- Ask about repository facts only when inspection leaves them consequentially unresolved; do not ask users to repeat an absent asset or unavailable proof already established by evidence.
- Treat undocumented compatibility, release cadence, storage, persistence, ranking, and proof as unavailable rather than inferring them.
- Omit sections or list items whose only content is unavailable proof; silence is the approved representation.
- Keep the exact structure fixed across variants; vary the strategic angle and copy, not the page anatomy or evidence.
- Use a private `/tailscale` preview when available; otherwise write a local static paginated preview and provide its path.
- Keep preview scaffolding outside the target repository; commit only the approved README, guide, and production assets.
- Use domain-native public wording; keep internal labels such as `first success`, `input`, `behavior`, and `result` out of published prose and comments.
